# Getting started

sphinx-ultra is a Rust reimplementation of `sphinx-build -b html`. This guide
installs it, runs a first build, and explains what the output tree contains
today. For the status of every subsystem see
[IMPLEMENTATION_STATUS.md](IMPLEMENTATION_STATUS.md); for configuration see
[configuration.md](configuration.md).

> **Before you start:** the project is pre-1.0. The build environment,
> cross-references, warnings and the `searchindex.js` / `objects.inv` /
> `.buildinfo` artifacts are real and verified against Sphinx 9.1.0, but each
> HTML page is still a placeholder (the escaped source text). Use sphinx-ultra
> today to validate a documentation tree the way `sphinx-build -W` does, not to
> publish a site.

## Install

### From crates.io

Requires Rust 1.85 or newer.

```bash
cargo install sphinx-ultra --locked
```

### Prebuilt binaries

Every [GitHub release](https://github.com/salioglu/sphinx-ultra/releases/latest)
ships archives for:

| Platform | Archive |
|---|---|
| Linux x86_64 (glibc) | `sphinx-ultra-<version>-linux-x86_64.tar.gz` |
| Linux x86_64 (static, musl) | `sphinx-ultra-<version>-linux-x86_64-musl.tar.gz` |
| Linux aarch64 | `sphinx-ultra-<version>-linux-aarch64.tar.gz` |
| macOS x86_64 | `sphinx-ultra-<version>-macos-x86_64.tar.gz` |
| macOS Apple Silicon | `sphinx-ultra-<version>-macos-aarch64.tar.gz` |
| Windows x86_64 | `sphinx-ultra-<version>-windows-x86_64.zip` |

Each archive has a `.sha256` file next to it. On Linux and macOS the install
script detects the platform, downloads the archive, verifies the checksum and
installs the binary into `~/.local/bin` (override with `INSTALL_DIR`):

```bash
curl -fsSL https://raw.githubusercontent.com/salioglu/sphinx-ultra/main/scripts/install.sh | sh
```

Read the script before piping it to a shell if that is your policy; it is
short. It does not modify your shell configuration.

### From source

```bash
git clone https://github.com/salioglu/sphinx-ultra.git
cd sphinx-ultra
cargo build --release
./target/release/sphinx-ultra --version
```

## First build

Point sphinx-ultra at an existing Sphinx project, the directory that holds
`conf.py`:

```bash
sphinx-ultra docs _build/html -b html
```

You get the same closing lines `sphinx-build` prints (`build succeeded` or
`build finished with problems, N warnings`), the same exit code, and an
output tree that today contains:

```
_build/html/
├── .buildinfo            # Sphinx's config + tags hash, byte-identical to sphinx-build's
├── .sphinx-ultra-cache/  # the persisted environment and per-document doctrees
├── _static/              # placeholder theme assets
├── index.html            # placeholder page: <html><body>escaped source</body></html>
├── …one .html per source document
├── objects.inv           # Sphinx 9.1 inventory of every label, document and py object
└── searchindex.js        # Sphinx 9.1 search index (IndexBuilder port, Snowball English)
```

Everything a project's *references* depend on is computed for real: a
`:ref:` to a missing label, a toctree entry that does not exist, a duplicate
label, a `py:function` registered twice, or a dangling `:py:class:` under
`-n` all warn with Sphinx's text, location and `[type.subtype]` category.

## The two command-line modes

### `sphinx-build` mode

Any invocation that does not start with one of the native subcommands is
parsed like `sphinx-build`, so a `Makefile` generated by `sphinx-quickstart`
works unchanged after `SPHINXBUILD = sphinx-ultra`:

```bash
sphinx-ultra SOURCEDIR OUTPUTDIR [FILENAMES...] [options]
sphinx-ultra -M html SOURCEDIR OUTPUTDIR      # make-mode: writes OUTPUTDIR/html
sphinx-ultra -M clean SOURCEDIR OUTPUTDIR     # empties OUTPUTDIR
```

| Option | Meaning |
|---|---|
| `-b html` | Builder. Only `html` is supported; other builders exit 2 |
| `-c PATH` | Directory containing `conf.py` (a file path also works) |
| `-d PATH` | Cache ("doctree") directory. Default: `OUTPUTDIR/.sphinx-ultra-cache` |
| `-D key=value` | Override a configuration value. Repeatable. See [configuration.md](configuration.md#overrides-on-the-command-line) |
| `-A name=value` | Set an `html_context` value. Repeatable |
| `-t TAG` | Define a tag (hashed into `.buildinfo`; `only::` evaluation is not implemented yet) |
| `-n` | Nitpicky: warn about every unresolved reference |
| `-q` | Quiet: no progress output |
| `-E` | Discard the saved environment and re-read every document |
| `-a` | Write all files (here: re-read everything, see below) |
| `-T` | Show a traceback on an unhandled error |
| `-j N` / `-j auto` | Parallel jobs for the read phase |
| `-W` | Turn warnings into errors: exit 1 after the build if any warning was logged |
| `--keep-going` | Accepted; collect-all is already the default, as in Sphinx 8.1+ |
| `-w FILE` | Also write warnings and errors to FILE |
| `-v`, `-vv`, … | More logging. A pre-set `RUST_LOG` wins over `-v`/`-q` |

sphinx-build mode is **incremental by default**: the environment and every
document's doctree are saved under the cache directory, and the next build
re-reads only documents that are new, changed, removed, or that depend on a
file that changed (an image, an included file). `-E` discards the saved
environment; `-a` re-reads everything.

Exit codes follow sphinx-build: `0` on success (with or without warnings),
`1` on build errors or on `-W` with warnings, `2` on usage errors, a missing
`conf.py`, an unsupported builder, or an invalid configuration. One
deliberate difference: a document that cannot be read is a build error here
and exits 1, where sphinx-build logs an error and still exits 0.

Two caveats. A source directory literally named `build`, `clean` or `stats`
must be written with a path prefix (`sphinx-ultra ./build _build`), because
those words select the native subcommands. And `FILENAMES` are accepted but
the full project is built, with a warning.

### Native mode

```bash
sphinx-ultra build  --source docs --output _build [--jobs N] [--clean] [--incremental] [-W] [-w FILE]
sphinx-ultra clean  --output _build
sphinx-ultra stats  --source docs
sphinx-ultra --config my-config.yaml build --source docs --output _build
```

`build` is a full read every time unless `--incremental` is given. `--clean`
empties the output directory first (safe together with `--incremental`: the
cache is cleared too). `--config` routes a `.py` file to the `conf.py`
parser and anything else to the YAML/JSON loader. `--verbose` and `--config`
are global options and go before the subcommand.

`stats` prints the number of source files, total lines, average and largest
file size, directory depth and a naive cross-reference count.

## Configuration discovery

Configuration is found in this order: `conf.py`, `sphinx-ultra.yaml`,
`sphinx-ultra.yml`, `sphinx-ultra.json`, then built-in defaults. `conf.py`
is **parsed, not executed**: single- and multi-line literals are read,
anything computed (`os.environ`, function calls, f-strings) is dropped with a
`conf.py:<line>` warning. The keys the build actually consumes, and the YAML
schema, are listed in [configuration.md](configuration.md).

## Incremental builds and the cache

The cache directory holds a blake3 fingerprint of the configuration, the
serialized `BuildEnvironment` (`env.bin`), one doctree per document, and the
intersphinx inventory cache. Any content-bearing configuration change
invalidates the whole cache; `-W`, `-n` and the order of `html_context`
entries are deliberately excluded from the fingerprint. Cached documents
still write their page on every build, so a warm build always produces a
complete output tree.

## Troubleshooting

**More detail.** `sphinx-ultra docs _build -vv`, or `RUST_LOG=debug
sphinx-ultra docs _build`. In native mode `--verbose` goes before the
subcommand.

**`Error: config directory doesn't contain a conf.py file`** (exit 2). In
sphinx-build mode a configuration is required; pass `-c` or create one. Native
`build` falls back to defaults instead.

**`Error: '…' is same as source directory!`** (exit 1). The output directory
may not equal or contain the source directory, as in sphinx-build.

**`unknown config value 'x' in override, ignoring`.** `-D` keys are checked
against the configuration schema; this warning counts toward `-W`.

**A broken `include` path builds clean.** Diagnostics that docutils records
inside the doctree (a missing or circular include, an unknown directive) are
not printed yet. This is a known limitation, listed in
[IMPLEMENTATION_STATUS.md](IMPLEMENTATION_STATUS.md#known-divergences-from-sphinx-910-m2-wave-45).

**`Setting up extension: …` on stdout.** Listing an extension has no effect
yet; the line is a stub and will go away with the extension ABI (M4).

**Markdown pages are empty.** `.md` files are discovered and get a placeholder
page, but no Markdown structure is parsed yet (MyST is M2 wave 6).
